# 批量写库优化效率对比（2026-11-01）

本报告比较同一台 Windows 主机、同一负载下的写库路径优化前后结果。优化前为提交 `51bbd07` 的运行时代码；优化后为当前工作树运行时代码，增加批次合并单遍处理、SQL 形状缓存和写库连接异常边界。两边各执行 3 次，表格使用中位数，同时保留每次原始数据。

## 负载和计时边界

- 6 或 60 个协议 RTU；每站 YC1000、YX1000、YK200、YT200。
- 每站 20 个周期；每个周期 YC/YX 共 2000 个值全部变化。
- 6 站为 240000 次点更新，60 站为 2400000 次点更新；使用真实 `spawn` 写库进程、`JoinableQueue` 和 SQLite 提交。
- 排空时间从并发生产开始到写库进程处理 STOP、提交全部事务并退出；包含线程构造、消息合并、序列化、跨进程传输、SQLite 更新和提交。
- 不连接现场设备；不把串口、CAN、IEC104、Modbus、BACnet 或 OPC 的网络响应时间计入。

## 优化内容和正确性

- `_flush_batch` 在验证时直接完成同一行合并，消除原先对每个点的第二遍展开、排序和复制。
- `_batch_update_sql` 使用有界 LRU 缓存重复的表、主键和字段形状；字段仍按确定顺序绑定，标识符继续经过校验。
- 写库连接打开失败现在会确认队列消息、记录错误并返回失败，让监督器按既有机制重建；事务失败仍回滚，锁错误仍重试。
- 三次 6/60 站压测均逐行核对最终 YC/YX 值、`_version=21`、质量状态、点数、`integrity_check=ok`、零外键违规和写库进程退出码 0。
- 新增批写测试覆盖混合表/站点、字段乱序、批内最后值、非法消息全批回滚、后续 SQL 失败回滚、锁重试和连接失败确认。

## 限制

本次性能结果是 Windows 本机临时 SQLite/IPC 基准，不是现场设备通信时延保证；Linux 尚未在本机实测。稳定值过滤和 5 秒心跳会降低实际日常写入量，满变化压测代表写库上限附近的压力。
