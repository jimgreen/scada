# SCDFE 多通道并发验收（2026-11-06）

已部署到 [C · 8877](http://127.0.0.1:8877/)、[S · 8878](http://127.0.0.1:8878/)、[T · 8879](http://127.0.0.1:8879/)。实库保持原有业务配置：T 通道 1 运行并监听 2404，C 的三个采集角色与 S 的九个模拟服务维持上线前的停止状态。额外通道和故障注入只在隔离库中使用。

## 发现与修复

| 复现条件 | 修复后的行为 |
|---|---|
| T 在同一 Web 实例停止慢通道时，另一通道也无法取得控制锁 | 只在同一通道串行执行；跨 Web 进程仍使用按通道的文件锁。 |
| T 通道表单打开期间仅发生普通周期心跳，按原版本保存返回 409 | 心跳只用一条 UPDATE 刷新本通道时间；不再读取整行或增加配置版本。启动、停止和真实配置修改仍会改变版本。 |
| S 协议实例更换 RTU 后，迟到的旧回调可能读取新通道的报文保存策略 | IEC104 和其他协议引擎在创建回调时绑定 RTU 与通道。已保存的新报文记录通道号，S 日志页可按该编号、RX/TX、服务、关键字组合筛选。旧报文在不指定通道时仍可查，不推测其历史归属。 |
| 切换通道时网络响应未到，旧点表仍提供编辑和删除 | C/S/T 切换范围时立即收起或清空旧操作，迟到的响应不能将旧内容覆盖回来。S/T 的编辑和删除携带读取时的版本；检测到冲突时拒绝覆盖另一名操作员的修改。 |
| 多通道日志查询在目录枚举中仍逐一匹配无关进程 | 指定进程时用它的文件名前缀缩小候选集，仍复核完整进程名；无关文件可以在获取额外文件属性前排除，目录链接与 Windows 联接点仍被排除。 |

## 并发测试与证据

- **共享数据库**：12 个线程分别写 12 个通道，每通道 80 个事务，共 960 个事务、2,880 个点更新。每批在同一事务内写入一对相反的遥测值和一条遥调值。C 的 HTTP 列表检查 309 次、S 检查 314 次，T 跨两张表读取同一事务快照 3,999 次。4,622 次读取全部符合配对关系、通道范围；全部点的最终值与版本计数正确。[压力结果](./scdfe_multichannel_20261106/contention.json) · [可复演脚本](./scdfe_multichannel_20261106/contention.py)
- **真实规约收发**：通道 1、11 使用 IEC104，10、100 使用 Modbus TCP；四个 Web 管理的独立转发进程在同一隔离库读取点号 1。四条连接各自读到本通道初始值及三轮修改后的值；两个 Web 用同一版本争写同一点，恰好一个成功，另一个返回 409。只开启 1 和 10 的报文保存，两个方向只找到对应通道，11、100 没有保存。停止 11 后，其余三个仍在线，并再次读取了两条 Modbus 连接。[回归用例](../tests/test_multichannel_concurrency.py)
- **实际浏览器**：人为延迟 RTU 10 的响应。C 页修改前仍展示 6 个旧行操作，修改后是 0；S/T 修改后也均为 0。另一个操作员修改同号点后，S/T 的旧表单提交均返回 409；两个通道的数据都符合预期。S 页按通道 10、1 依次筛选 RX，分别只显示 HEX=0a、HEX=01。[C 改前](./scdfe_multichannel_20261106/c-before.txt) · [C 改后](./scdfe_multichannel_20261106/c-after.txt) · [S/T 浏览器结果](./scdfe_multichannel_20261106/operator.txt)
- **完整回归**：最终 459 项，458 通过、0 失败、1 跳过，253.781 秒。跳过项因本机 Windows 账户无符号链接创建权限。完整套件包括原有三 Web 采集、写入、转发、命令、重启的联调，以及 IEC104、Modbus、OPC、BACnet、CAN 等已有用例。[完整输出](./scdfe_multichannel_20261106/full_final.txt)
