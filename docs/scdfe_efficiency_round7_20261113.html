多通道监控：批量提交与即时诊断

S 端通信监控过去先读取数据库旧诊断，再逐通道刷新状态，导致同一响应中的收发计数和持久化诊断相差一轮。本轮先收集状态、一次提交，再读取已提交诊断，减少多 RTU 监控的数据库提交和重复关联查询。

真实本机 HTTP 通信监控接口；隔离 SQLite WAL 数据库；IEC104、Modbus TCP、CAN 服务混合配置并保持停止。两轮预热后交替执行新旧实现各 15 次，表中为中位数。前后使用相同数据库、连接池和动态变化的计数，比较包含序列化与本机 HTTP 往返。

每个通道额外的 RTU→通道查询被消除，使用一次共享关联查询。单通道结果受 Windows 调度和计时波动影响，3.3% 差异不作为稳定收益结论；300 通道的 300→1 次提交为确定的结构性减少。完整样本包含离群值，未剔除。

正确性与并发

  • 进程监控和通信监控共用批量状态发布；单 RTU 请求仍只处理所选 RTU，独立服务 status() 和启停调用保留原行为。
  • 按固定顺序取得服务锁，再收集状态并进入数据库事务，提交后释放，避免旧监控快照覆盖较新的停止状态。事务开始后不再反向申请服务锁。
  • 任意通道写入失败会回滚整批状态，并清除本次发布的限频缓存，使下一次刷新能够重试；接口返回 HTTP 503 与 runtime_snapshot_failed。
  • 聚合监控查询只接受 GET；错误使用 POST 返回 405。通道启动和停止仍使用原有独立 POST 控制接口。

批量期间会短暂持有所选服务的锁，因此启停和其他监控请求可能等待当前批次完成。本次验证覆盖停止操作与监控并发排序，尚未给出大量活动连接下的最大锁等待时间。

页面操作

S“通信监控”和“进程监控”照常刷新即可使用优化后的接口；通信测试页继续按当前 RTU 读取，不需修改通道或 RTU 定义。本轮不修改数据库结构，也不依赖页面编辑来驱动规约的数据同步。

适用边界

本轮测量的是监控接口与运行态数据库开销，不代表 IEC104、Modbus 或 CAN 的现场线缆吞吐同比例提高。规约测试使用本机 TCP 回环和 CAN virtual，总线硬件、串口、环境与长时间稳定性未在本轮验证。T 转发仍限 IEC104 与 Modbus TCP。其他已知能力限制见规约接口说明。
