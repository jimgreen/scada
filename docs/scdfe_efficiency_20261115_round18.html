SCDFE 第十八轮优化与验证

2026-11-15 · 纯 Python · 多 RTU 监控数据库读取与诊断处理

定位及修改

上一轮普通 5 秒刷新没有事务数收益且测得耗时增加。本轮检查发现，64 个 IEC104/Modbus TCP/CAN 混合服务每次监控采集有 85 条配置读取 SQL、42 个独立读事务；通用协议的引擎诊断取得两次，同一响应和数据库快照可能不同。性能剖析还显示，诊断 JSON 的通用类型检查和递归转换是主要 CPU 调用来源之一。

S 按参数表分组读取所选 RTU 配置，RTU 名称/通道和参数共用一个读取快照。按 SQLite 变量限额分段，单 RTU 请求只取该站；没有跨请求配置缓存，下一次刷新可见外部修改。显式配置覆盖、缺省值、运行中绑定和合法性检查保留。单服务配置采用一次关联查询，仍保留默认 RTU 与参数的一致读取事务。

通用协议状态每次只读取一次引擎诊断，接口与保存路径复用。C/S/T 共用诊断编码先处理常见标量，避免大量不必要的类型检查；特殊类型及 JSON 兼容格式保持。运行状态使用一次 executemany 批量调用，保持原行数、版本、顺序保护、生命周期锁和事务原子性。上一轮的重要状态即时保存、普通统计限流和外层事务回滚重试仍通过回归。

修改前的隔离基线复现了逐行 SQL 调用、单服务两条配置查询、64 通道 85 条读取及引擎诊断重复读取。最初新增测试中有两处夹具错误（重复读取同一服务的全部行、使用了不存在的参数列），另有诊断夹具将属性写成方法；修正夹具后重新在基线上确认重复读取 2 次，新实现为 1 次。保留原始失败记录，不将夹具错误算作程序缺陷。
