时间接口边界

本机把 2024-02-29T23:59:59.900000+00:00 直接交给原生 Information 构造器时，线上时间为 2024-02-29T10:59:59.900000+00:00，偏移 -13 小时。返回值为无时区的本地时间。此项测试的是原生 API，不是用户在 HMI 输入事件时间的流程。

pybind 的 chrono 转换会忽略输入 datetime 时区，并返回本地 naive datetime；这与绑定源码和公开文档一致。pybind11 时间转换说明。CP56 本身没有时区标识，工程必须约定 UTC 或地方时；本报告独立对端约定 UTC，受控发送夹具显式转换到原生要求的本地 naive 输入。此转换仅在测试夹具中，未伪装成产品时间修复。

时间 IV、SU、替代标志和测点质量是不同字段。原始帧能携带这些位，但当前业务快照未暴露它们。lib60870 信息对象与 CP56 API。

S 测试使用现有扫描锁暂停一次扫描，在此期间完成 21 次独立提交；释放后由 S 自主扫描上送。C 测试让 101 条真实报文先到达，再运行一次真实 collect_once 与 ChannelWorker 写库。T 使用真实共享数据库和 refresh 方法。这里控制扫描窗口以确定性复现合并，不把人工暂停时间当作正常运行延迟。

同点连续变化在 C 的最新值字典中覆盖；写库只更新四遥当前值和本地刷新时间，T 又从该快照生成报文。源码与当前表结构未发现持久化事件日志及消费游标。T 重启后总召只返回当前值属于正常 GI 行为；缺少历史恢复的依据是没有事件存储和重放机制，不能要求总召本身回放全部历史。

超载测试先发送 16384 条短报文，再开始接收和 ACK，等待流量排空后统计，无重复收到事件。原生发送调用均返回接受，缓冲溢出未向调用者返回逐事件失败。1024 是按最大 ASDU 分配缓冲的容量参数；小帧可以容纳更多条，不能把它理解为严格的 1024 条上限，也不能保证无限事件无损。

已修复与仍需补齐的内容

已修复：IEC104Master.from_store 原来总是填入通道默认 data_type，覆盖点映射 type_id；带时标 30/31/32 以及普通双点／步位置信息可能被注册成单点。现在优先使用显式点类型，保留调用者覆盖和未映射时的默认值。修复前回归复现 5 个类型失败，修复后实际 S 数据库→C 接收链路通过。

能力接口：C/S/T 的 /api/protocol-capabilities 新增 monitoring_semantics=latest_point_snapshot、soe_event_log=false 和 soe_lossless_forwarding=false，避免把 spontaneous=true 理解为完整 SOE。

代码回归：广域回归首轮：2 failed, 121 passed, 108 subtests passed in 220.31s (0:03:40)；两项调度停止／重载测试单独复验：2 passed。首轮失败记录保留，未修改这两项测试或其业务代码。 类型映射、SOE 解码、原有 IEC104 收发及能力 API 检查通过；专项验收仍有 9 项未通过。回归通过项和复验结果不能掩盖 SOE 功能缺口。

  1. S 独立库需要追加式事件记录，值／质量修改与事件生成同事务提交；保留事件序号、源时间、原始状态与时间标志。
  2. C 接收需要独立事件队列，批量写入共享业务库，保留 COT、CA、IOA、类型、原始 CP56 和接收序号；不能按点号去重覆盖事件。
  3. T 从事件日志按消费游标读取并转发，跨重启保存进度，明确重传／去重、确认和离线保留策略；C/T 继续只经数据库交互。
  4. 建立队列容量、溢出告警和背压策略，分别测线上吞吐、持久化吞吐、端到端延迟及恢复能力；最新值表继续服务现有画面。

上述四项是后续实现清单，本轮未宣称已经完成；也未要求 GI 充当事件历史查询。
