先选对服务

要找现场原始值，先看 C；要模拟设备或验证某种规约，去 S；要让远方主站读到采集值，去 T。生产采集和转发不要求 S 在线。

S · 8878模拟源站或测试对端C · 8877采集、写库、下发命令T · 8879映射源点并对外转发

上行：设备（或 S 模拟源站）→ C 采集 → SQLite 源点 → T 映射 → 远方主站。
下行：远方主站 → T 接收遥控/遥调 → C 写库 → C 通信线程下发 → 设备回读。

四遥表示什么如何确认
YC · 遥测连续数值，如电压、功率或温度。对照源点与远方读数；同时看质量。
YX · 遥信离散状态，如开关位置。在测试源改变状态，检查两端是否同步。
YK · 遥控下发开/合等离散命令。核对目标、命令处理时间，再读回设备状态。
YT · 遥调下发设定值，如功率目标。核对比例、偏移和单位，再读回实际设定值。

读懂一个按钮：数据实际存在哪里

对象保存位置 / 所有者哪个动作会改变它
RTU、现场规约与四遥源点S：db/scdfe_s.sqlite3；C/T：db/scada.sqlite3。两库采用同样的表名：fes_rtu_define、各规约参数/辅助表、fes_{yc,yx,yk,yt}_define。S 新增、修改、删除只写 S 库；C 的定义和版本不变。C 从 S 采到的值通过规约进入业务库。
进程控制与在线状态C：fes_scdfe_c_define、fes_process_define 及 RTU 线程状态。T：fes_scdfe_t_define 的运行字段、进程所有权锁。启动/停止发出控制请求，后台进程登记 PID、状态和心跳；手动刷新只重新读取它们。
S 协议配置与测试值监听配置在库旁 JSON；协议线程拥有活动连接、模拟寄存器或 IEC 站内值；S 主站诊断轮询的最新值保存在内存。“保存配置”“从站更新”“主站单次采集”影响的位置不同，详见 S2–S4。
T 点映射与对外值fes_scdfe_t_point_define 保存映射；T 从源点表读值，将当前值交给协议栈。编辑映射不写源点；远方 YK/YT 才经 C 写库 IPC 提交命令。
报文策略与历史各服务独立策略 JSON；数据字节写各进程小时日志。日志正文不在业务点表中。调试开关影响后续写文件；查询条件、翻页、导出只改变看到的结果。

准备 / 首次运行

打开 Web，先确认数据库

Windows 从项目根目录打开 PowerShell。已部署的系统直接访问对应端口；初次部署可用 Python 3.11 建立环境。以下命令按本仓库布局编写。

Set-Location D:\codex\scada
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

三个 Web 各占一个终端。按需运行对应命令，浏览器访问 http://127.0.0.1:端口/；已有服务占用端口时直接访问，不要重复启动。

# C：采集管理
.\.venv\Scripts\python.exe -B -m scdfe_c.web.server --host 127.0.0.1 --port 8877 --db db/scada.sqlite3
# S：规约测试
.\.venv\Scripts\python.exe -B -m scdfe_s.web.server --host 127.0.0.1 --port 8878 --db db/scdfe_s.sqlite3
# T：转发管理
.\.venv\Scripts\python.exe -B -m scdfe_t.web.server --host 127.0.0.1 --port 8879 --db db/scada.sqlite3

逐个打开 /api/health，确认 status 为 ok，并核对 database 的绝对路径。8877（C）和 8879（T）应返回同一业务库，8878（S）应返回另一个文件和 database_role: simulator。S 的 Web 和独立规约命令均默认使用 db/scdfe_s.sqlite3；误把 --db 指向业务库会拒绝启动。Linux 从仓库根目录运行相同模块，将解释器替换为 .venv/bin/python。

区分两类端口：8877–8879 提供管理页面；IEC 104、Modbus 等规约端口由通道配置。Web 可访问只证明页面服务正常，不代表采集线程或转发通道已经启动。

01 / 现场采集

scdfe_c：采集、写库和命令下发

C 按 RTU 配置连接现场设备。自动守护进程扫描定义，为符合条件的 RTU 启动通信线程；写库进程批量提交采集数据。采集支持 IEC 104、Modbus TCP、Modbus RTU、CAN、BACnet/IP 和 OPC UA。

管理入口 http://127.0.0.1:8877/　左侧：进程监控 / 通信监控 / 运行日志 / 数据与定义

1.1　让一个 RTU 开始采集

  1. 在「数据与定义 → RTU 与通道」建站或选择已有 RTU，核对 RTU 编号、通道号和规约。RTU 编号用于定位源站；通道号用于连接配置和报文保存，两个编号不必相同。
  2. 在 RTU 行使用「通道维护」「通道参数」设置连接，再配置该规约的点地址。以 Modbus TCP 为例，核对远端 IP、协议端口、单元号、召唤功能码、寄存器起始地址和长度；在辅助表中把返回数据映射到本 RTU 的点。
  3. 切到「遥测」「遥信」「遥控」「遥调」标签，选定 RTU，再维护点号、名称等字段。先建一个便于核对的点；切换 RTU 后再确认当前选择，避免改到相同点号的另一站。
  4. 启用需要自动采集的 RTU，在「进程监控」启动主进程，确认写库进程投入运行；「通信监控」检查该 RTU 的线程状态和连接错误。返回四遥页，对照现场变化检查值、更新时间和质量。

1.2　区分自动守护、单站调试和 TCP 指令服务

运行方式何时使用判断结果
自动守护多 RTU 正常采集，推荐从 Web 管理。也可从终端运行 python -m scdfe_c --db db/scada.sqlite3。进程监控看主进程和写库进程；通信监控看具体 RTU。
单 RTU 调试停用目标 RTU 的自动采集并等其释放后，再调试；同一个 RTU 同时只允许一个通信所有者。只查看该 RTU 的调试日志。默认不发送命令，--send-commands 是显式启用命令的选项。
TCP 指令服务外部系统需要通过认证的 TCP 接口提交 YK/YT 时，从进程监控启动 command-server 并核对其配置。提交成功表示命令已写入数据库；设备是否执行，仍要看通信线程处理和设备回读。
# 例：测试库中已配置的 RTU 7，独立采集 10 个成功周期
.\.venv\Scripts\python.exe -B -m scdfe_c --db db/scada.sqlite3 --rtu-id 7 --max-cycles 10

1.3　检查一条遥控或遥调

在选定 RTU 的遥控/遥调页选择目标点并提交。脚本可使用 POST /api/rtus/{rtu_id}/commands/{yk|yt}/{pnt_no}；TCP 指令服务则接收按行发送的 UTF-8 JSON，用 request_id 标识同一请求。检查 cmd_time（提交时间）与 cmd_handle_time（处理时间）；若命令仍待处理，先查写库、线程和该 RTU 日志，再核对设备回读，不要把 HTTP 接收成功当成现场执行成功。

其他进程如何发令？见第 7 章：同机与跨服务器接入、代码下载及回读。

只想看一条通道的原始收发？在「RTU 与通道」的报文保存列操作，或从「运行日志」选择具体通道。详细步骤见报文保存与检索。

1.4　逐项操作与后台数据流

C1 建站 · C2 配点 · C3 启停 · C4 采集 · C5 下发 · C6 删除 · C7 单站调试

C1

建站与配置通道

操作
在「数据与定义 → RTU 与通道」点「新增记录」。例：RTU 37101、通道 38101、规约 modbus-tcp，填名称并保存。选回这行，用「通道维护」改通道属性，用「通道参数」填远端主机、端口和单元号。
后台数据流
  1. 新增 RTU → POST /api/rtus → fes_rtu_define 保存站、通道号和规约
  2. 通道维护 → /api/rtus/37101/channel → 更新同一站记录
  3. 通道参数 → /api/rtus/37101/channel/parameters → 按规约选择参数表；本例为 fes_channel_modbus_tcp_define
核对结果
刷新后重新打开同一 RTU，三个层次分别核对：站号 37101、通道号 38101、远端 IP/端口及单元号。这里只是在写定义，还没有发生网络连接。
不符合时
若提示 RTU 已有通道，应编辑当前通道；不要靠再建一行来替换。改变规约前，先核对原规约参数和辅助表。
C2

定义四遥点，接上协议地址

操作
在数据页选择 RTU 37101 →「遥测」→「新增记录」，建点 1，填写编码、名称。再配置 Modbus 召唤和数据映射：单元 1、功能码 03、起始地址 0、数量 1，把地址 0 的结果对应到 YC 1。选定 RTU 后从「辅助表」选择对应表；本例的 call_seq 均为 0、cnt=1、reg_addr=0、if_yx=0、trans_type=2。
后台数据流
  1. 测点页 → /api/rtus/37101/points/yc → fes_yc_define，主键包含 RTU 和点号
  2. 召唤定义 fes_channel_modbus_define_call（call_seq、iplace、inum、icode）→ 数据映射 fes_channel_modbus_define_data（同一 call_seq、cnt、reg_addr、trans_type）
  3. 自动守护在扫描定义时识别该 RTU 的变化，再由对应主站按新定义采集
核对结果
选回 RTU 37101 / YC 1。仅出现这一行说明定义已存在；要证明采集有效，还要让源端改变值，看到本点值和刷新时间随之变化。
不符合时
有点但读数不动：逐一比对召唤地址、长度、功能码及数据映射；业务点号 1 不要求等于协议地址 0。
C3

启动、观察和停止自动采集

操作
启用目标 RTU 的自动通信，进入「进程监控」启动主进程。需要独立查看写库时，检查 writer 的状态；再到「通信监控」按 RTU 找通信线程。一键启动会影响参与一键操作的目标，调试单站时优先选具体目标。
后台数据流
  1. 进程按钮 → POST /api/processes/control（target、action）→ 进程控制器处理启停
  2. 进程登记 fes_process_define；主进程读取控制参数 fes_scdfe_c_define 和 RTU 的启用状态
  3. 守护按 RTU 启停通信线程 → 协议主站连接对端；Web 重新查询 PID、心跳、线程状态
核对结果
同时核对主/写库进程、该 RTU 的线程、点值变化。停止后等状态回落和通道释放，再切换单站调试。
不符合时
Web 健康但没有数据时，不要先重启 Web。先查 RTU 是否启用、主进程是否持有运行权、writer 是否在线、该 RTU 的连接错误是什么。
C4

区分页面刷新与真正采集

操作
打开「遥测」或「遥信」，选 RTU 并记下值与刷新时间；在模拟源端将 42 改成 43，允许一个采集和页面刷新周期，再看同一条记录。
后台数据流
  1. 现场回包 → RTU 线程解码并形成点值、质量、刷新时间；遥测可包含原始值与工程值
  2. 正常自动采集将更新批次送入写库队列 → writer 合并并提交到 fes_yc_define / fes_yx_define
  3. Web 刷新走 GET 读取已提交的行；T 扫描读取同一库，但没有经过这个网页
核对结果
以源值 43、C 值 43、质量正常和刷新时间为依据。点收到回包、更新入队、数据库提交和页面刷新是不同时间点。
不符合时
只看到通信字节时先核对解码映射；能解析但数据库不更新时再查 writer 状态和日志。重复点击页面刷新不会触发现场采集。
C5

下发 YK/YT：把“已提交”追到“已执行”

操作
切到「遥控」或「遥调」→ 选 RTU、点号 → 打开下发窗口。YK 选 0/1；YT 填工程值并核对上下限。确认窗口中的 RTU 与点号后，在模拟对象上提交一次。
后台数据流
  1. C Web → POST /api/rtus/{rtu_id}/commands/{kind}/{pnt_no}，携带当前版本与 value → 校验闭锁、范围、未处理命令
  2. Web 自己的写事务更新 fes_yk_define / fes_yt_define 的 value、cmd_time、status 和版本 → 返回 HTTP 202 / pending
  3. RTU 线程读取待处理命令 → 调用规约发送 → 写回处理状态和 cmd_handle_time；另读设备反馈确认动作
核对结果
cmd_time 大于 cmd_handle_time 表示待下发；处理后 status=1 对应“已下发”，status=3 对应“下发失败”。设备是否真正到位，应以反馈遥信、遥测或协议读回为准。
不符合时
闭锁、上一命令待处理、工程范围错误或版本冲突时先查原因。外部 TCP 指令服务与 T 走 writer IPC，和本页直接提交事务是两条不同入口。
C6

删除前确认影响范围

操作
在 RTU 列表发起删除，先核对预览中的 RTU 与各关联表数量；若只是暂停采集，改启用状态，不进入删除确认。删除后还需检查 T 是否仍引用该源点。
后台数据流
  1. 页面 → GET /api/rtus/{id}/delete-preview → 按站统计关联记录，只读
  2. 确认 → 对 RTU 执行 DELETE → 存储层按 RTU 清理关联定义及点表 → 列表重新加载
核对结果
确认站号、影响点数及关联条目；退出预览不等于执行删除。业务库里被删除的源点不会因 T 仍有映射而恢复。
不符合时
若目标是保留配置供以后重启，应取消删除。若版本不一致，重新读取记录和预览，不要直接覆盖。
C7

单站调试后切回自动采集

操作
停用目标 RTU 的自动通信，等待原线程释放。进「进程监控」选择独立调试 RTU，或按 1.2 的命令行运行有限次数。先保持默认不下发命令，结束调试、确认退出后再恢复 RTU 自动启用。
后台数据流
  1. 调试进程按 RTU 号获取该站独占锁 → 从同一数据库查通道和规约配置
  2. 调试线程采集该站 → 通过自己的写事务更新对应点表；调试日志按 scdfe_c-debug-rtu-{id} 区分
  3. 结束/停止 → 协议连接和库连接关闭，释放 RTU 锁 → 自动守护可重新接管
核对结果
在调试进程和该站日志中核对真实规约、采集次数及源点变化；退出后检查自动线程已恢复。
不符合时
若提示 RTU 已被自动通信或另一调试进程占用，先停止原所有者并等待释放。不要仅更换 Web 端口来抢占同一 RTU。

02 / 规约测试

scdfe_s：模拟设备、主动采集与协议联调

S 可以模拟现场源站，也可以作为主站主动连接设备。先选角色：要给 C 提供模拟寄存器，选「服务端」；要让 S 主动去读一台 Modbus 设备，选「主站」。两者连接方向相反。

管理入口 http://127.0.0.1:8878/　首页「测试总览」按规约和角色选择测试页。

初始化 S 专库：直接启动 S 会创建空的 db/scdfe_s.sqlite3。如果要用 C 的通道和四遥定义作为测试起点，在目标文件尚不存在时，从项目根目录执行一次：
.\.venv\Scripts\python.exe -B -m scdfe_s.migrate --source db/scada.sqlite3 --destination db/scdfe_s.sqlite3

命令以只读方式打开源库，复制 RTU、四遥点及其显示值、规约参数和地址映射；不复制进程状态、待执行命令或 T 的转发表。未配置通道且无子记录的 RTU 会列入报告；有关联点或参数时，命令会中止并提示补全定义。目标文件已存在时拒绝覆盖。复制完成后，两库独立维护。S 的规约配置和小时日志位于库旁；需要保存报文时，在 S 页面单独开启对应通道。

用同一编号验证隔离

  1. 在两边选一个未占用的测试编号，例如 RTU 501、通道 601；C 建名为“采集站”的记录，S 建名为“模拟站”的记录，各建 YC 1、YX 1、YK 1、YT 1。不要使用现场正在运行的站。
  2. 在 S 更改站名、点名或初值。在 C 刷新：同号站仍是“采集站”，点定义不变。删除 S 的一个点，再删除 S 的测试通道；C 刷新后四类点仍在。
  3. 要验证数据真的从 S 到了 C，请启动 S 的协议监听，在 C 单独配置远端地址、单元号和采集映射，然后通过实际报文核对；同号既不必需，也不会自动配对。

2.3　模拟一个 Modbus TCP 从站

  1. 在「通道数据」准备一个测试 RTU，进入「四遥数据」建立 YC 点。此模拟从站以点号减一作为协议地址；若要测试写入，另建 YK/YT 点，并按它们的模拟地址配置对端。
  2. 打开「Modbus TCP 从站」，选同一 RTU，填写监听 IP、一个空闲协议端口及单元号，保存配置后启动该服务。C 的远端 IP、端口和单元号必须与这里对应。
  3. 在该规约页对 YC 做增量更新，或一次提交一批点；用对端读寄存器核对新值。通信监控应能看到服务运行，日志可用于核对请求和响应。
  4. 如果报错说明“数据库已提交，但规约发布未确认”，分别重新读取库值和协议值；不要把这种情况当成整批未提交而直接重复发送。

需要仅从命令行启动一个测试 RTU 时，下面是可选入口。例中的 7 必须已配置，15020 必须空闲，不要和同一 Web 已启动的监听器重复绑定。

.\.venv\Scripts\python.exe -B -m scdfe_s.run_modbus_tcp_server --db db/scdfe_s.sqlite3 --rtu-id 7 --mode server --bind-ip 127.0.0.1 --listen-port 15020

核对结果

不符合时
校验或事务失败：整批未提交。若提示库已写入但发布未确认，先比对点表与实际寄存器；YC 与 YT 映到同一槽位的同一批次不能给两个不同值。

后台数据流
  1. 采集按钮 → POST /api/modbus-tcp/poll → 协议主站读取对端 → 最新值进入该测试服务的内存缓存，页面叠加显示

核对结果
一次采集后 S 协议页可显示新值，但诊断轮询不会覆盖 C 的采集点表。下发则是实际协议写请求，应从对端回读验证。
不符合时
不要把测试主站的缓存当成 C 已经入库；若 S 看到新值而 C 没变，应单独查 C 的连接、地址与 writer。

操作

  1. 增量更新 → POST /api/iec104/update/incremental → 四遥点先写 S 库
  2. 服务更新站内点值 → 有活动连接时可发送 YC/YX；没有活动连接时仅更新站内值
  3. 远方总召/接收上送 → 与点号、IOA、类型和质量比对；下行命令另从命令记录查看
核对结果

不符合时
如果库已提交但发布失败，先查连接和服务错误，再用总召确认当前站内值。用普通 HTTP 页面刷新不会生成 IEC 总召。

停止协议、改站、清理测试数据

操作

后台数据流
  1. 停止 → 对协议服务 POST stop → 服务关闭协议引擎并解除当前 RTU 绑定，定义与小时日志保留
  2. 修改点 → PATCH 具体点号，更新记录的版本号；确认删除点 → DELETE 具体点号，只操作当前 RTU、类型和点号
  3. 删除整站 → DELETE /api/channels/{rtu_id} → 按 RTU 清理关联记录；与仅停止协议是两种动作
核对结果
停止后协议服务显示已停止，站和测点仍可查看。切换到新站后重新连接，并用新站的测试值核对。
不符合时
若目标只是释放监听端口或暂停模拟，选择停止；不要删站。删除只清理 S 专库；C 的同号站点仍在。如果该站正为 C 模拟设备，停止服务可能使 C 通信中断，这是协议连接中断，不是 C 定义被删除。

03 / 四遥转发

scdfe_t：把源点映射给远方主站

T 不替代 C 的现场连接。它从 C 的数据库读取源点，以 IEC 104 或 Modbus TCP 服务端的身份向远方提供数据；每个转发通道有独立进程、监听地址和点映射。

管理入口 http://127.0.0.1:8879/　配置在「通道数据」「四遥数据」；状态在「进程监控」「通信监控」。

3.1　建立、映射、启动

  1. 打开「通道数据」/channels.html，新建通道，填写编码、名称、规约、监听地址和空闲端口。IEC 104 填公共地址；Modbus TCP 填单元号。记录新通道的 channel_id。
  2. 打开「四遥数据」/points.html，先选转发通道，再建点映射。填写转发类型、转发点号、源 RTU、源点号，启用该映射。同一通道内，类型与转发点号的组合必须唯一。
  3. 到「进程监控」/processes.html 启动该通道，检查状态、PID 和心跳；在「通信监控」/communication.html 核对监听配置。进程已运行不等于远方主站已经连入。
  4. 让远方主站连接协议端口：IEC 104 发总召，Modbus TCP 读指定数据区和地址。与 C 四遥页的源值对照；若测试 YK/YT，还要检查源点命令时间及现场回读。

3.2　三个编号不要混用

字段示例含义
channel_id10T 的转发通道编号，决定在哪个监听进程配置映射。
source_rtu_id / source_pnt_no37101 / 1C 库中数据的来源；点的类型由该映射的 YC/YX/YK/YT 决定。
kind / pnt_noYC / 101T 通道内的转发点身份，不必等于源点号。
对端协议地址Modbus 输入寄存器地址 0对端实际读写的地址。IEC 104 则按公共地址、IOA 与类型标识配置。

Modbus 还需核对数据区、地址、数据类型、比例和偏移；多寄存器值按两端约定核对字节序/字序。IEC 104 能传递质量码：已启用源点丢失时保留上次值并标记无效；Modbus 没有等价质量位，只看到寄存器旧值时，要回到 C 查源点。

3.3　运行和变更

Web 启停是日常入口。要在终端单独运行一个已配置且当前未被占用的通道，可以使用下列命令；示例通道号应替换为自己的测试通道。

.\.venv\Scripts\python.exe -B -m scdfe_t --db db/scada.sqlite3 --channel-id 10

运行时约每秒检查配置。名称、扫描/上送周期等改动不应断开现有连接；改监听端口、规约或生效中的源点映射可能重建服务。选择可中断时段，记录旧配置，变更后重新读一次源点。若编辑页面出现版本冲突，应重新载入该记录后再改。

验证下行需要写库：T 通过 C 写库服务提交 YK/YT。T 能上送 YC/YX，并不意味着写库和 C 下发线程一定可用。

T1

新建监听通道：先保存，再单独启动

操作
打开 /channels.html →「新建通道」，填写编码、名称、规约、监听 IP 和端口。例：Modbus TCP、127.0.0.1:15021、单元号 1、扫描周期 100 ms。保存后记下系统返回的通道号，以下用 10 举例。

  1. 通道表单 → POST /api/trans/channels → 校验规约、字段和值
  2. 保存 fes_scdfe_t_define 的通道定义 → 页面重读列表和详情；此时不等于协议端口已监听
核对结果
列表可找到准确编号，监听 IP/端口和规约符合预期。多通道要分别选择端口，不能拿 Web 端口当协议端口。

T2

添加点映射：对照两个点号和一个地址

操作

  1. 表单 → POST /api/trans/channels/10/points → 在 fes_scdfe_t_point_define 写映射

不符合时

T3

启动、停止和检查进程所有者

操作

后台数据流
  1. 启动 → POST /api/trans/channels/10/start → Web 串行处理该通道启停，写启动意图并启动独立进程
  2. 工作进程持有该通道的系统锁，加载定义和映射 → 建立 IEC/Modbus 监听 → 更新通道表的状态、PID、心跳
  3. 停止 → POST /api/trans/channels/10/stop → 清除启用标志，等待工作进程退出、释放锁并记录停止状态
核对结果
进程监控以持锁判断实际所有者；PID 只是辅助。心跳更新表示进程活着，不代表远方收到新值。
不符合时
显示错误时读该通道小时日志，查端口冲突或启动失败。另一个通道的 PID 和锁不证明本通道已启动。
T4

远方读取 YC/YX：谁更新寄存器，谁发总召

操作
让 C 的 YC 点由 42 变到 43；在远方主站发读取。Modbus 示例发功能码 04、单元 1、地址 0、数量 1；IEC 104 示例由远方主站按正确公共地址总召，核对返回 IOA、值与质量。
后台数据流
  1. T 扫描 fes_yc_define / fes_yx_define 中源 RTU 和点号的 value、status → 组成当轮源点快照
  2. Modbus：变化值批量更新 T 的寄存器 → 对端主动读；IEC：更新站内值及质量 → 总召或上送由协议栈发出
  3. C/T 页面显示源数据或映射，协议客户端才是远方实收的证据
核对结果
同一次变化分别核对 C 源点、T 映射、协议实读三处。IEC 源值丢失时应看 IV；Modbus 旧值本身不能证明连接健康。
不符合时
若 T 已运行但一个点错，优先核对源 RTU/点号与数据区、IOA/地址，而非重启所有转发通道。
T5

远方写 YK/YT：确认回复之后还要查什么

操作
为测试 YT 建可写保持寄存器映射，例如地址 10、比例 2、偏移 10，绑定 C 已存在且允许下发的 YT 点。远方写原始值 8，记下时刻；随后查 C 的命令点和 S 的现场寄存器。
后台数据流
  1. 远方协议写 → T 按通道映射解码工程值（8 × 2 + 10 = 26）
  2. T 调用 C 写库 IPC → writer 校验并提交源 YT 的 value=26、cmd_time → 成功后 T 才能确认该提交
  3. C 通信线程发现待处理命令 → 通过其采集规约下发 → 更新处理状态和时间 → 读回实际设备/模拟源
核对结果
依次看到 T 接收、C 源 YT=26 且 cmd_time 更新、处理状态、模拟源端寄存器=26。C 的 TCP command-server 不是这条 T 路径的必经点。
不符合时
writer 未启动、源点未建、闭锁或已有命令待处理都可能使本次提交失败。不要只看 T 网络应答就认定设备已经执行。
T6

变更或删除通道时确认哪些数据会保留

操作
只改名称或扫描周期，在「通道数据 → 编辑」保存即可；换监听端口或有效映射时安排可中断时段，保存后从新地址重连。废弃通道时，先查清该通道的全部点映射，再确认删除。
后台数据流
  1. 编辑 → PATCH 通道或映射 → 写 T 定义表；工作进程定期比较有效配置，必要时重建协议服务
  2. 删除 → DELETE /api/trans/channels/10 → 先校验版本并协作停通道 → 再删除此通道的映射及通道定义
核对结果

不符合时
版本冲突时重读；停止期间定义被他人修改，应重新核对对象后再操作。

从模拟源站到远方：验证一个遥测点

以下为本机测试示例，编号和端口仅用于说明。选用未使用的编号与端口；S 使用独立模拟库，C 和 T 使用同一测试业务库。已有正常运行的现场通道不参加这个例子。

位置示例配置本步可观测结果
① S 模拟源站建 RTU 37100，单元号 1，YC 点 1 对应模拟保持寄存器地址 0（无符号 16 位）。Modbus TCP 从站监听 127.0.0.1:15020；启动后将 YC 设为 42。独立主站用功能码 03 读地址 0、数量 1，得到 42。
② C 采集建 RTU 37101，Modbus TCP 连接同一 IP、15020、单元号 1。设置功能码 03 的召唤与数据映射，让保持寄存器地址 0 对应本 RTU 的 YC 点 1。启用采集后，C 的 RTU 37101 / YC 1 显示 42，质量正常。
③ T 对外转发建一条 Modbus TCP 转发通道，监听 127.0.0.1:15021，单元号 1。新增 YC 转发点 101，源为 RTU 37101 / YC 1；对外为输入寄存器地址 0、uint16、比例 1、偏移 0。启动该通道；远方主站用功能码 04 读 15021 的输入寄存器地址 0，得到 42。
④ 确认是实时链路在 S 将值从 42 改成 43；依次查看 C 的源点、T 的远方读数。两处都变为 43。只看到一次相同旧值不足以证明采集仍活跃。

反向验证时，只对模拟点建立 YK 或 YT 映射。例：把一个 YT 映射到 T 的可写保持寄存器；若比例为 2、偏移为 10，远方写入原始值 8，应在 C 的对应命令点看到工程值 26，再从 S 对应的写寄存器读回 26。三处的点号与地址要逐一核对，不必相等。

规约 01

IEC 60870-5-104

IEC 104 用于远动监视与控制。在本系统中，C 主站连接 S 或现场从站；同一连接上的站由公共地址标识，点由信息对象地址（IOA）和类型标识确定。一次总召能帮助区分“配置里有点”和“从站实际返回了点”。 IEC 标准说明

服务角色：C：IEC104 采集；S：IEC 104 服务端；T：可配置为 IEC 104 转发服务端。

1.1　新增

在「RTU 与通道」新增 RTU 37201、通道 38201，规约选 iec104。点该行「通道参数」，填远端 IP、端口（示例 127.0.0.1:2404）、rtu_addr=1。在「遥测」建点 1，再到「协议参数 → IEC104点映射」新增 YC 1，填 io_address=16385（0x4001）、type_id=13。类型应与设备约定一致。

1.2　查询

筛选 RTU 37201，打开 IEC104 点映射，按类型和点号找到 YC 1。核对公共地址与 IOA 后，在 S 的 IEC 104 页启动对应站，让主站总召；对照收回的 IOA、值和质量。

1.3　修改

在 YC 1 行点「编辑」，例如把 IOA 从 16385 改为 16386；公共地址要在该站「通道参数」中另改。两端同步调整后重新总召，核对新 IOA 的响应。

1.4　删除

在点映射表选中 37201 / YC / 1 删除，刷新确认该 IOA 的显式映射不再存在。再到「遥测」确认 YC 1 仍在。规约可按起始地址生成默认映射，若目标是彻底撤点，还应核对现场点表及总召结果。

规约 02

Modbus TCP

Modbus TCP 通过网络读写线圈、离散输入、保持寄存器或输入寄存器。连接成功后，还要用正确的单元号、功能码和地址访问目标数据区。界面里的寄存器地址是报文中的地址，不要直接照抄设备手册的 4xxxx 编号。 Modbus TCP 与功能码说明

服务角色：C：采集主站；S：TCP 主站和从站各有页面；T：可作为 Modbus TCP 转发从站。

2.1　新增

建 RTU 37202，选 modbus-tcp；在「通道参数」填 127.0.0.1:15020、unit_id=1。建本地 YC 1。在「辅助表」依次建 MODBUS通道（irtuaddr=1）、召唤（call_seq=0、icode=3、iplace=0、inum=2）和数据映射（cnt=1、if_yx=0、reg_addr=0、trans_type=2）。示例为无符号 16 位保持寄存器。

2.2　查询

筛选 RTU 37202，在「辅助表 → MODBUS数据」按 id 找映射；打开「详情」看地址。在 S 从站将源寄存器更新为 43，然后由主站发 FC03，按单元号 1、起始地址 0 核对报文与 C 的 YC 1。

2.3　修改

在数据映射行「编辑」，把 reg_addr 从 0 改为 1；本例召唤覆盖地址 0、1，不必扩大范围。若改到范围外，应一起修改召唤的起始地址或数量。刷新配置后比较新地址的实读值。

2.4　删除

先删除目标 MODBUS数据行，再查询同一 id，确认记录消失。核对 YC 1 仍在；如还要删召唤，先检查其他映射是否使用同一 call_seq。仅删除一条映射不需要删除整站。

规约 03

Modbus RTU（串口）

Modbus RTU 通过串口传输。同一条总线需匹配波特率、数据位、校验位、停止位和从站地址；串口能打开并不代表目标从站已经应答。召唤、寄存器映射与 TCP 使用同一组辅助表。 Modbus 串行线路指南

服务角色：C：串口主站；S：RTU 主站、RTU 从站模拟或串口；T：无串口 RTU 转发通道。

3.1　新增

建 RTU 37203，选 modbus-rtu。在「通道参数」选实际串口，示例 COM3、9600、8 位、无校验 N、1 停止位、单元 1。在「遥测」建 YC 1，再建 MODBUS通道、召唤（FC03，地址 0，数量 2）及数据行（cnt=1，地址 0，trans_type=2）。COM3 是填写示例。

3.2　查询

筛选本站分别查串口参数、召唤序号和 MODBUS数据行。S 的 Modbus RTU 主站可做单次采集；实线测试时核对从站地址、请求、应答与 CRC 错误。虚拟串口或模拟模式不能证明现场接线正确。

3.3　修改

串口速率在「通道参数」中改，例如从 9600 改到 19200，并同步对端设置；点地址在「MODBUS数据 → 编辑」中改，例如 reg_addr=1。串口不能同时被两个进程独占；重新打开连接后核对目标地址应答。

3.4　删除

删除本站的数据映射行并按 id 查询；检查本地 YC 1 不受影响。只想释放串口时，应停止对应规约服务。删除召唤前查清其他点是否引用它。

后台与复核：通道参数 → fes_channel_modbus_rtu_define；点映射 → fes_channel_modbus_define_data。在 C 查询通道参数：GET /api/rtus/37203/channel/parameters；查询图示映射：GET /api/tables/fes_channel_modbus_define_data/rows/37203。创建用集合 POST；修改用单条 PATCH，删除用单条 DELETE。编辑现有行应携带该行读取时的 _version 作为 If-Match；发生冲突先刷新再核对。

规约 04

CAN / CAN FD

CAN 通过帧标识符区分消息。一帧可以包含多个测点，解析时还需要字节偏移、位长度、字节序和比例。CAN FD 支持更长的数据段，并可配置数据阶段速率；收发两端的帧格式、控制器能力和物理总线必须一致。 CiA：CAN FD 帧与速率

服务角色：C：总线采集；S：CAN 主站、服务端模拟或接口；T：无原生 CAN 转发。

4.1　新增

建 RTU 37204，选 can。示例使用 interface=virtual、channel=scada-doc、bitrate=500000、data_bitrate=2000000、fd=1。建 YC 1，在「协议参数 → CAN报文解析」填 frame_id=291（0x123）、is_fd=1、字节偏移 0、位偏移 0、位长 16、value_type=uint、byte_order=big、比例 1。

4.2　查询

按 RTU / 类型 / 点号找到映射。到 S 的 CAN 页查看收帧 ID、帧格式和数据；示例按大端解析，高低字节 00 2B 表示 43。若看到帧而点不变，核对标准/扩展标识、FD 标志和位段。

4.3　修改

编辑映射，把 frame_id 从 291 改为 292（0x124），或调整比例与偏移；发送方必须使用相同帧 ID 和格式。改仲裁速率或数据阶段速率时到通道参数设置；重连后以实际收帧核对。

4.4　删除

删除本站 CAN报文解析行，查询 RTU / 类型 / 点号并核对本地 YC 1 仍在。同一帧可供多个点使用，不应连带删除其他位段；删映射不会停止物理总线上的发帧。

7.3　跨服务器：只用标准 TCP 和 JSON

线格式：每条指令新建一个 TCP 连接，发送一行 UTF-8 JSON（末尾一个 LF，\n），读取一行 JSON 应答后关闭；每行含换行最多 64 KiB。每次都带令牌。任何能按此格式读写套接字的语言均可接入。

请求字段填写规则
op、token示例使用 "command"；也可使用 "submit_command"。token 与 C 配置一致。
request_id调用方生成的非空字符串，最长 128 个字符。保存编号和原始目标、值，用于辨认同一业务动作。
rtu_id、point_no均为正整数，分别是 C 的 RTU 号、该类型中的点号；不要传小数、布尔或带引号的编号。
kind、value"yk"：发 0 或 1，具体动作含义见点表；"yt"：发有限工程数值，在点定义允许范围内。YC/YX 是反馈，不是发令类型。

一条遥调请求示意（令牌为占位符），以及成功回执的关键字段节选：

{"op":"command","request_id":"demo-yt-001","rtu_id":37101,"kind":"yt","point_no":1,"value":26,"token":"<共享令牌>"}
{"ok":true,"request_id":"demo-yt-001","command_status":"pending","item":{"rtu_id":37101,"pnt_no":1,"value":26,"cmd_time":1794000000000,"status":0}}
scdfe_tcp.py
import argparse
import getpass
import json
import os
import socket

p = argparse.ArgumentParser(description="通过 TCP 提交一条 YK 或 YT")
p.add_argument("host", help="C 服务器可达地址，或隧道本地端点")
p.add_argument("port", type=int)
p.add_argument("request_id", help="本次业务动作的唯一编号")
p.add_argument("rtu", type=int)
p.add_argument("kind", choices=("yk", "yt"))
p.add_argument("point", type=int)
p.add_argument("value", type=float)
a = p.parse_args()
# 自动化进程可由凭据管理器注入环境变量；交互运行时隐藏输入。
token = os.environ.get("SCDFE_COMMAND_TOKEN") or getpass.getpass("TCP token: ")
req = dict(op="command", request_id=a.request_id, token=token, rtu_id=a.rtu,
           kind=a.kind, point_no=a.point, value=a.value)
wire = json.dumps(req, allow_nan=False).encode("utf-8") + b"\n"
try:
    with socket.create_connection((a.host, a.port), timeout=15) as sock:
        sock.sendall(wire)
        with sock.makefile("rb") as stream:
            line = stream.readline(65537)
    if not line.endswith(b"\n") or len(line) > 65536:
        raise ValueError("响应不完整或过长")
    ack = json.loads(line.decode("utf-8"))
    if ack.get("ok") and ack.get("request_id") != a.request_id:
        raise ValueError("响应编号与请求不一致")
except (OSError, ValueError) as exc:
    raise SystemExit(f"{a.request_id}: {exc}；收发结果未确认，请先核对点状态。")
if not ack.get("ok"):
    raise SystemExit(f"{a.request_id}: {ack.get('code')} / {ack.get('error')}")
print(json.dumps({"request_id": ack["request_id"], "state": ack["command_status"],
                  "cmd_time": ack["item"]["cmd_time"]}, ensure_ascii=False))

7.4　已有 Web 接入：先读版本，再提交

在 C 管理机或已有受控 Web 接入的环境使用本例。先 GET /api/rtus/37101/points/yt/1 读取 item._version；再 POST /api/rtus/37101/commands/yt/1，带 If-Match: "3" （例：刚读到的版本为 3，双引号是请求头的一部分）和 Content-Type: application/json，请求体只有 {"value":38}。C Web 在自己的事务里校验并写点，成功返回 HTTP 202 和 command_status=pending。不要把 TCP 的 token 或 request_id 放进此接口。

scdfe_web.ps1
param(
    [Parameter(Mandatory)][string]$Web,
    [Parameter(Mandatory)][int]$Rtu,
    [Parameter(Mandatory)][ValidateSet('yk','yt')][string]$Kind,
    [Parameter(Mandatory)][int]$Point,
    [Parameter(Mandatory)][double]$Value
)
$ErrorActionPreference = 'Stop'
$base = $Web.TrimEnd('/') + "/api/rtus/$Rtu"
$pointUrl = "$base/points/$Kind/$Point"
$row = (Invoke-RestMethod -Uri $pointUrl).item
$ack = Invoke-RestMethod -Method Post -Uri "$base/commands/$Kind/$Point" `
    -Headers @{'If-Match' = ('"{0}"' -f $row._version)} -ContentType 'application/json' `
    -Body (@{value=$Value} | ConvertTo-Json -Compress)
$stamp = [long]$ack.item.cmd_time
Write-Output "accepted: $($ack.command_status), cmd_time=$stamp"
# 轮询只读点接口；不再次 POST。按 cmd_time 确认看到的是本条指令。
for ($i=0; $i -lt 20; $i++) {
    $r = (Invoke-RestMethod -Uri $pointUrl).item
    if ([long]$r.cmd_time -ne $stamp) { throw 'Point now holds a different command; check logs.' }
    if ([long]$r.cmd_handle_time -ge $stamp) {
        $r | Select-Object value, cmd_time, cmd_handle_time, status
        if ($r.status -ne 1) { throw 'Command was not reported as sent; check channel logs.' }
        return
    }
    Start-Sleep -Milliseconds 500
}
throw 'Still pending; inspect the worker and device. Do not resend automatically.'

7.5　怎样确认设备收到的是这条指令

  1. 接收与入库。TCP 服务校验令牌和字段 → 经本机 IPC 交给数据库写进程；HTTP 入口则校验点版本 → 由 C Web 提交事务。两条路径均检查目标点、闭锁、未完成的上一条指令和遥调范围。成功后，fes_yk_define 或 fes_yt_define 的目标行更新 value、cmd_time、status=0 和版本。保存回执里的 cmd_time；pending 表示已入库。
  2. 线程下发。目标 RTU 的 C 通信线程检测命令版本变化，读取待处理点并调用规约适配器。去 C「遥控／遥调」刷新该点（见图 C5），或 GET 同一个点接口。先确认 cmd_time 等于回执值；若已变化，当前行属于另一条指令，应结合业务记录与通道日志核查。点表仅存当前状态，不是按请求号查询的历史表。
  3. 结果与反馈。cmd_time > cmd_handle_time 表示仍待下发；处理时间追上本条命令且 status=1 表示 C 报告已下发，status=3 表示下发失败。再读对端独立反馈，例如线圈、保持寄存器、开关反馈遥信或实测遥测；不能用命令点上自己写入的 value 代替设备反馈。需要对照发送报文时，仅打开该通道的报文保存，复核后关闭。
看到什么怎样处理
连接被拒绝、超时、读不到端点核对 C 主机、入口端口、绑定地址、访问规则和进程心跳。远端不读取 C 的端点文件；确认没有把 8877、设备规约端口或调用机回环当成指令服务。
TCP unauthorized / invalid_command / command_rejected分别核对令牌、请求字段、写进程返回的具体原因。后者可由点不存在、闭锁、上一条还在等待或 YT 越界触发。先纠正原因，再决定是否创建新动作。
TCP 等不到回执、writer_unavailable 或 request_in_progress先按站、点、预期值和提交时刻查当前点、日志与设备反馈。近期同编号同内容的重试可以复用结果；同编号改目标或值会返回 request_id_conflict。去重是进程内有限缓存（最近 2048 条），重启或淘汰后不能保证防重复；结果不明时不要换号重发。
HTTP 428 version_required、409 version_conflict 或 409 command_pending重新 GET，看是谁或哪条命令改变了点；核对是否仍需发令。一个点只容纳一个待处理命令；上一条处理完再发下一条，不能靠覆盖点值排队。

示例实测：从本页下载并运行三个脚本：同机 Python 向 C RTU 37101 / YK 1 发 1，独立读取 S 模拟从站线圈地址 2，结果为真；TCP Python 向 YT 1 发 26，保持寄存器地址 4 读回 26；停掉 TCP 指令服务后，Web 示例发 38，同一寄存器读回 38。错误令牌、相同编号改值和缺失／过期的 Web 点版本均被拒绝。客户端与服务在不同进程中通过本机网络连接；跨服务器的路由、防火墙、隧道及现场设备仍须在部署网络验证。

按现象找到下一步

现象先查接着做
Web 打不开或提示端口占用核对是管理端口还是规约端口，检查监听进程和 /api/health。若页面已在线直接使用；若是协议监听冲突，为测试通道选择空闲端口，同步修改对端。
C 有进程，YC/YX 不动在通信监控按 RTU 查看线程状态，在四遥页核对值、刷新时间和质量。核对自动启用、对端地址、单元号/公共地址和协议辅助表；对比 RX/TX 后再改映射。
S 启动后读不到点确认选择了主站还是服务端，绑定的 RTU 是否正确，服务是否正在运行。两端核对数据区、功能码、地址起点和字节序；串口/CAN 先排除链路配置不一致。
T 已启动，远方值为零或停在旧值先读 C 的同一源 RTU、同类型、同点号，再查 T 的映射是否启用。核对远方读的是 T 的协议端口和转发地址。IEC 104 同时检查质量码；Modbus 仅凭数值不能判定新鲜度。
有上行，没有下行检查 C 写库服务、目标 YK/YT 点和通信线程，区分命令提交与实际处理。对照 cmd_time、cmd_handle_time、发送报文与对端反馈；测试时只用可回读的模拟点。
日志为空或只有普通日志查看该服务、该通道的实际保存状态；核对所选小时、进程和 RX/TX 方向。开关生效后制造一次新流量，从“全部匹配文件”重查；不要用另一个服务的开关判断本端是否保存。
修改不生效或被拒绝先看是否选错 RTU/通道、数据库路径或编辑版本。重新打开记录，核对当前版本；监听/映射变更后，到进程监控和通信监控确认生效，再用对端读取。
